# M08-S03 — Versionar candidatos e promover com rollback

**Status:** pending

**Milestone:** [M08 — Avaliação e melhoria controlada](MILESTONE.md)
**Dependências:** [M08-S02](../M08/M08-S02.md)
**Requisitos:** [R16](../REQUIREMENTS.md#r16), [R17](../REQUIREMENTS.md#r17)

## Resultado esperado

Versionar candidatos e promover com rollback. A capacidade pertence à plataforma e deve funcionar com qualquer bot autorizado.

## Áreas previstas

configuration registry; deployment policies; dashboard review. Caminhos definitivos serão confirmados na implementação; são áreas de responsabilidade, não arquivos já entregues.

## Trabalho a construir

- [ ] Criar candidato de prompt/modelo/ferramenta/política com versão e hipótese.
- [ ] Executar bateria fixa e comparar qualidade, segurança, latência e consumo antes de recomendar.
- [ ] Registrar aprovação explícita de promoção e selecionar bots/projetos piloto.
- [ ] Permitir rollback para versão anterior; mudanças de código seguem PR e validação normal.

## Critérios de aceite

- [ ] Nenhum diagnóstico modifica produção sem validação e aprovação de promoção.
- [ ] Candidato reprovado não substitui configuração vigente.
- [ ] Rollback identifica runs afetados; não reescreve histórico nem muda snapshot de run já em execução.
- [ ] Melhoria só é recomendada com critérios de qualidade atendidos e trade-offs apresentados.

## Validação e evidências exigidas

- [ ] Testar candidato aprovado/reprovado, promoção concorrente e rollback.
- [ ] Testar versão de ferramenta incompatível com runtime anterior.
- [ ] Aplicar os gates comuns de [validação](../VALIDATION.md), registrando comando, revisão, resultado e limitações.
- [ ] Executar verificações negativas de permissão pertinentes; comprovar ausência de dependência de ID/nome do bot.

## Telemetria obrigatória

candidate_created, candidate_evaluated, promotion_approved, policy_promoted, policy_rolled_back.

Aplicar o [contrato transversal](../TELEMETRY.md): correlação, versão efetiva, tentativas, duração, resultado/erro, redaction, acesso e retenção. Para operações com efeito, persistir intenção e recibo; resultado incerto deve ser reconciliado. Testes devem consultar os eventos persistidos, não apenas verificar que um callback foi chamado.

## Falhas e compatibilidade

Usar os estados e regras de [arquitetura](../ARCHITECTURE.md). Falhas mantêm evidência, não ampliam permissões nem apagam trabalho do usuário. Interfaces existentes continuam compatíveis; ativação segue capacidade/política do bot e do projeto.

## Registro de entrega

- Evidências automatizadas: pendente.
- Evidências reais / aceite de operador: pendente ou não aplicável com justificativa.
- Limitações e riscos residuais: pendente.
- Não alterar para concluída apenas porque código compilou ou testes simulados passaram.
