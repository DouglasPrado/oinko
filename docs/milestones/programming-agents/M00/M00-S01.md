# M00-S01 — Modelar capacidade de programação e ProgrammingRun

**Status:** pending

**Milestone:** [M00 — Contratos compartilhados e linha de base](MILESTONE.md)
**Dependências:** Nenhuma; início do plano.
**Requisitos:** [R01](../REQUIREMENTS.md#r01), [R02](../REQUIREMENTS.md#r02), [R03](../REQUIREMENTS.md#r03)

## Resultado esperado

Modelar capacidade de programação e ProgrammingRun. A capacidade pertence à plataforma e deve funcionar com qualquer bot autorizado.

## Áreas previstas

packages/agent-runtime; packages/bots; packages/workspaces; contratos do SDK. Caminhos definitivos serão confirmados na implementação; são áreas de responsabilidade, não arquivos já entregues.

## Trabalho a construir

- [ ] Definir ProgrammingRun, Step, OperationReceipt, Artifact e versões dos contratos.
- [ ] Relacionar bot, conversa, projeto, Task existente, worktrees e runs sem transformar Task em conversa.
- [ ] Definir portas de persistência, execução, publicação e telemetria; contratos de erro e autorização.
- [ ] Mapear requisitos nos blueprints 24–26 e criar adendo de blueprint antes de implementar comportamentos novos.

## Critérios de aceite

- [ ] Dois bots podem usar o mesmo serviço com configurações diferentes, sem condicionais por nome ou ID.
- [ ] Task continua representando o trabalho/worktree; um run representa uma execução persistida e pode referenciar PRs por repositório.
- [ ] Estados e transições seguem ARCHITECTURE.md, incluindo terminalização com operações ainda incertas.
- [ ] SDK não depende de Docker, dashboard, Telegram ou GitHub App.

## Validação e evidências exigidas

- [ ] Testar contratos serializáveis, transições inválidas e referências entre entidades.
- [ ] Revisar dependências entre pacotes e compatibilidade das APIs existentes.
- [ ] Aplicar os gates comuns de [validação](../VALIDATION.md), registrando comando, revisão, resultado e limitações.
- [ ] Executar verificações negativas de permissão pertinentes; comprovar ausência de dependência de ID/nome do bot.

## Telemetria obrigatória

run_created, run_state_changed; validar envelope e snapshot das políticas.

Aplicar o [contrato transversal](../TELEMETRY.md): correlação, versão efetiva, tentativas, duração, resultado/erro, redaction, acesso e retenção. Para operações com efeito, persistir intenção e recibo; resultado incerto deve ser reconciliado. Testes devem consultar os eventos persistidos, não apenas verificar que um callback foi chamado.

## Falhas e compatibilidade

Usar os estados e regras de [arquitetura](../ARCHITECTURE.md). Falhas mantêm evidência, não ampliam permissões nem apagam trabalho do usuário. Interfaces existentes continuam compatíveis; ativação segue capacidade/política do bot e do projeto.

## Registro de entrega

- Implementação/PR: pendente.

- Evidências automatizadas: pendente.
- Evidências reais / aceite de operador: pendente ou não aplicável com justificativa.
- Limitações e riscos residuais: pendente.
- Não alterar para concluída apenas porque código compilou ou testes simulados passaram.
