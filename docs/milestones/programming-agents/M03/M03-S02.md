# M03-S02 — Despachar em segundo plano e ordenar fila por bot

**Status:** completed — aceite com runId imediato, fila durável por bot, dedupe, controle independente, confirmação antes de um segundo trabalho na conversa e chat tradicional preservado testados (inclusive desconexão no Docker real).

**Milestone:** [M03 — Execução durável e controle do trabalho](MILESTONE.md)
**Dependências:** [M03-S01](../M03/M03-S01.md)
**Requisitos:** [R04](../REQUIREMENTS.md#r04), [R08](../REQUIREMENTS.md#r08), [R11](../REQUIREMENTS.md#r11)

## Resultado esperado

Despachar em segundo plano e ordenar fila por bot. A capacidade pertence à plataforma e deve funcionar com qualquer bot autorizado.

## Áreas previstas

agent-runtime/service e host; dispatch de canais. Caminhos definitivos serão confirmados na implementação; são áreas de responsabilidade, não arquivos já entregues.

## Trabalho a construir

- [x] Separar aceite do pedido e execução; devolver runId imediatamente após persistência.
- [x] Manter um run de programação ativo por bot e fila durável para novos trabalhos.
- [x] Enviar status/pause/resume/cancel por via de controle independente da fila.
- [x] Reconhecer novo pedido versus esclarecimento do run ativo com contexto e confirmação quando ambíguo.

## Critérios de aceite

- [x] Fechar página ou conexão HTTP após aceite não aborta o trabalho durável.
- [x] Dois bots podem avançar separadamente; mesma worktree mantém exclusão entre escritores.
- [x] Pedido repetido com mesma chave não cria dois runs.
- [x] Chat legado preserva comportamento e não passa involuntariamente a criar trabalhos.

## Validação e evidências exigidas

- [x] Testar aceite seguido de desconexão e reinício com fila pendente.
- [x] Testar dois bots, três pedidos no mesmo bot e status durante comando longo.
- [x] Aplicar os gates comuns de [validação](../VALIDATION.md), registrando comando, revisão, resultado e limitações.
- [x] Executar verificações negativas de permissão pertinentes; comprovar ausência de dependência de ID/nome do bot.

## Telemetria obrigatória

run_queued, run_dispatched, request_deduplicated, queue_wait_measured.

Aplicar o [contrato transversal](../TELEMETRY.md): correlação, versão efetiva, tentativas, duração, resultado/erro, redaction, acesso e retenção. Para operações com efeito, persistir intenção e recibo; resultado incerto deve ser reconciliado. Testes devem consultar os eventos persistidos, não apenas verificar que um callback foi chamado.

## Falhas e compatibilidade

Usar os estados e regras de [arquitetura](../ARCHITECTURE.md). Falhas mantêm evidência, não ampliam permissões nem apagam trabalho do usuário. Interfaces existentes continuam compatíveis; ativação segue capacidade/política do bot e do projeto.
