**Milestone:** [M02 — Entendimento do projeto e edição precisa](MILESTONE.md)

## Resultado esperado

Revisar diff e executar verificações pertinentes. A capacidade pertence à plataforma e deve funcionar com qualquer bot autorizado.

## Áreas previstas

runner Git; checks service; context tools. Caminhos definitivos serão confirmados na implementação; são áreas de responsabilidade, não arquivos já entregues.

## Trabalho a construir

- [ ] Capturar estado Git anterior e diff do run sem atribuir alterações do usuário ao bot.
- [ ] Executar testes/lint/build escolhidos pelo pacote afetado e permitir verificação ampliada justificada.
- [ ] Resumir saída com referências ao log completo e classificar falha de código vs ambiente.
- [ ] Produzir evidências associadas ao commit ou hash da árvore ainda não commitada.

## Critérios de aceite

- [ ] Pequena alteração não exige reescrever arquivo inteiro.
- [ ] Check skipped/timeout/falha de infraestrutura não é reportado como aprovado.
- [ ] Diff final relaciona arquivos tocados e mudanças preexistentes.
- [ ] Teste só comprova a revisão realmente executada; nova edição invalida aprovação anterior.

## Validação e evidências exigidas

- [ ] Realizar bug com teste em sandbox Docker e conferir diff/resultado.
- [ ] Testar saída extensa, falha de instalação e alteração de arquivo depois do check.
- [ ] Aplicar os gates comuns de [validação](../VALIDATION.md), registrando comando, revisão, resultado e limitações.
- [ ] Executar verificações negativas de permissão pertinentes; comprovar ausência de dependência de ID/nome do bot.

## Telemetria obrigatória

git_diff_captured, check_started, check_finished; comando, diretório, revisão e resultado.

Aplicar o [contrato transversal](../TELEMETRY.md): correlação, versão efetiva, tentativas, duração, resultado/erro, redaction, acesso e retenção. Para operações com efeito, persistir intenção e recibo; resultado incerto deve ser reconciliado. Testes devem consultar os eventos persistidos, não apenas verificar que um callback foi chamado.

## Falhas e compatibilidade

Usar os estados e regras de [arquitetura](../ARCHITECTURE.md). Falhas mantêm evidência, não ampliam permissões nem apagam trabalho do usuário. Interfaces existentes continuam compatíveis; ativação segue capacidade/política do bot e do projeto.

## Registro de entrega

- Implementação/PR: pendente.
- Revisão e ambiente testados: pendente.
- Evidências automatizadas: pendente.
- Evidências reais / aceite de operador: pendente ou não aplicável com justificativa.
- Limitações e riscos residuais: pendente.
- Não alterar para concluída apenas porque código compilou ou testes simulados passaram.
